# Phase 6: Quote and order

## Overview

Spec A7 (price list, placed here because it adds to the quote basket), A8, A9, A10, A11, A14 (contact form endpoint + component), B5, B6. Server reprices every submit; order prices are snapshotted; staff enter shipping fee and walk the status flow; dynamic VietQR (amount + content) built in `emvco.ts` and rendered as SVG once staff confirm the total; a SePay bank-notification webhook auto-marks exact-match transfers PAID, everything else goes to a MANAGER review queue [W1, W2]. Public forms are protected from day one (honeypot, Turnstile, one per-IP limit per form) [RT#5]; phase 8 only adds edge rules. Email notification for new orders/quotes is part of this phase and a go-live blocker [RT#6].

Owner decisions 2026-10-29 (Validation S2): **W1** SePay = notifier (money stays in the company account) + our own EMVCo QR; Casso is the fallback if SePay does not support the owner's bank; payOS rejected (gateway, customer pays on vendor page, conflicts with the on-page QR and spec D). **W2** policy A: exact match -> system sets PAID (audit actor `BANK_WEBHOOK`); anything else -> REVIEW, never changes order state; manual MANAGER "Đã nhận tiền" stays as fallback. **RT#6 amended by owner decision W2: PAID may be set by MANAGER or by the authenticated exact-match webhook.** Source: [bank webhook report](../reports/researcher-261029-bank-webhook-services-report.md) s.2, s.5, s.6.

## Requirements

- `/don-hang/[code]` [RT#5]: code, status steps, items, totals, bank block + transfer content = order code (A10). Data always fetched by code + phone (no link token). QR timing [V2, W1]: in PENDING the bank block shows account number + transfer content as text only, no QR (shipping fee not set yet, amount not final); once staff confirm (CONFIRMED with shipping fee) it shows the dynamic VietQR with amount = total + content, and the amount-freeze rule below applies; after PAID it shows "Đã nhận tiền" instead of the QR.
- `/tra-cuu-don`: phone + code -> `/don-hang/[code]` (A11).
- `/bang-gia`: all visible SKUs by category (Mã hàng, Tên, ĐVT, Quy đổi, Giá; hidden-price SKUs show "Liên hệ" via `PublicPriceRedactor` [RT#4]), filter category/brand, code search, qty inputs, "Thêm vào báo giá", "Tải Excel", "In / Lưu PDF" (print CSS).
- Admin `/admin/requests` per `docs/wireframes/admin-quotes.html`: filter column, unified table + totals row, expandable detail with step bar, items (list vs promo price per line), internal note, totals (Tổng tiền hàng, Giảm đã áp = `discount_total` + `discount_note`, Phí giao hàng input, Khách cần trả), actions; tab "Liên hệ" for contact messages; header bell counter.
- Quote flow: Mới -> Đã báo giá -> Chốt | Hủy. Order flow: Chờ xác nhận -> Đã xác nhận -> (Chuyển khoản: Đã nhận tiền) -> Đã nhập KiotViet (+ mã đơn KiotViet) -> Đang giao -> Hoàn tất; Hủy from any non-terminal.
- Payment destination controls [RT#6 amended by W2]: "Đã nhận tiền" (PAID) is set either manually by a MANAGER or automatically by the authenticated SePay webhook on an exact match (actor `BANK_WEBHOOK`); never by EDITOR. Manual PAID records `paid_amount` (mismatch vs total requires a note and shows a "Lệch số tiền" warning); webhook PAID records `paid_amount` = the matched transfer amount (= total by definition). Once the amount QR is visible (BANK_TRANSFER order in CONFIRMED) line, qty and fee edits are frozen except through an explicit "Cập nhật số tiền" re-issue with a reason, which the customer page shows as a visible note; cancelling a PAID order shows a refund warning and requires a note. EDITOR keeps other status changes and shipping fee (phase-2 matrix). Manual MANAGER "Đã nhận tiền" stays as the fallback when the webhook is down, disabled or a transfer lands in REVIEW.
- Bank webhook (SePay) [W1, W2]: auto-PAID only on an exact match (order code found in content + amount = order total + receiving account = configured + direction in + order is BANK_TRANSFER in CONFIRMED). Under/over/duplicate payments, unknown codes, wrong account, COD, PENDING or already-PAID orders are never auto-PAID: they go to the REVIEW queue (MANAGER links to an order or dismisses with a note). Admin order panel shows `paid_amount` and the linked bank transactions. Design: Architecture "Bank webhook".
- "Chờ nhập KiotViet" = COD orders in CONFIRMED + BANK_TRANSFER orders in PAID (never BANK_TRANSFER in CONFIRMED) [contract fix]; one predicate `OrderStatusMachine.awaitsKiotVietEntry()` used by the admin filter and the bell (no dashboard: owner decision A).
- Exports: quote Excel + print page; order Excel for KiotViet entry + print slip. PDF = browser print-to-PDF from print CSS pages, no server PDF library; Excel stays server-side (decided [V6]).
- Notifications [RT#6]: email to `notify.ownerEmail` on new order, new quote and new contact message (Spring Mail SMTP); admin bell as in-app backup; Zalo optional, out of scope.

## Architecture

```
Browser form ─POST /api/public/orders {submissionId, lines, expectedTotal, turnstileToken, website, ...}─> Caddy ─> Spring
  PublicFormGuard + OrderService.submit, in this order [RT#5]:
   1 honeypot `website` non-empty -> 400
   2 submissionId already stored -> 200 existing order view (replay: no limit, no Turnstile, payload ignored)
   3 limiter.peek(ipKey) -> >= 5 successful creates in 10 min -> 429 + Retry-After   (ipKey = IPv4 or IPv6 /64)
   4 OrderPricingService.price(lines, today, tiers) -> expectedTotal != computed -> 409 PRICE_CHANGED {pricedCart (redacted)}   (Turnstile token not consumed)
   5 TurnstileVerifier.verify(token, ip) -> fail -> 400 CAPTCHA_FAILED
   6 CodeGenerator("DNA") -> persist order + items snapshot -> limiter.record(ipKey)
   7 audit ORDER_CREATED; AFTER_COMMIT @Async -> NotificationPort.newOrder() (email)
   201 {order view} -> browser saves {code, phone} in sessionStorage, clears order basket -> /don-hang/{code}
  Client: on any non-2xx the Turnstile widget is reset before the next attempt.
/don-hang/[code] (client component, no-store): phone from sessionStorage -> POST /api/public/orders/lookup {code, phone}
   -> renders status; bank block: PENDING = text only; CONFIRMED + fee = emvco payload (with amount) -> qrcode SVG
   no stored phone (new device, shared URL) -> lookup form with code prefilled
```

- Pricing (`sales/pricing/OrderPricingService`): per line `PriceRules.effectivePrice`; checks SKU visible, product published && ACTIVE, order lines need `price_visible && price != null` (`SKU_NOT_ORDERABLE`), qty 1-9999, <= 50 lines, duplicate SKUs merged. `subtotal = Σ unit_price*qty` over priced lines (unit price is already post-promo; per-line promo stays visible as `list_price` vs `unit_price`); tier = highest `discount.tiers` threshold <= subtotal (post-promo; open Q4); `discountTotal = round(subtotal*pct/100, HALF_UP)` (0 when no tier); `discountNote` = short text, e.g. "Ưu đãi 2% cho đơn từ 1.000.000đ" (null when 0); `total = subtotal - discountTotal + (shippingFee ?? 0)`. One discount figure only [owner decision B]: no per-tier fields, no next-tier hint. Tiers are empty until phase 7, code path tested now. `POST /api/public/cart/price` is the same function in dry-run mode for basket pages; its response and the 409 `PRICE_CHANGED` body pass through `PublicPriceRedactor`: hidden-price lines carry null price fields + `priceVisible:false` and are excluded from every computed total [RT#4].
- Codes (`sales/CodeGenerator`): prefix + 6 chars of Crockford base32 `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (SecureRandom); unique index + up to 5 retries. Orders `DNA`, quotes `BG` (Q7). Input normalisation for lookup: uppercase, drop spaces/hyphens, `O`->`0`, `I`/`L`->`1`.
- Phone: digits only, `+84`/`84` -> `0`, must match `^0\d{9,10}$`; stored raw + `phone_norm`.
- Idempotency [RT#5]: client generates `submissionId` (UUID v4) when the basket page opens and keeps it until a 2xx; unique index on `quote_request.submission_id` and `customer_order.submission_id`; a replay returns the stored request (200) so double-clicks and retries after a timeout never create duplicates.
- Lookup [RT#5]: `POST /api/public/orders/lookup {code, phone, turnstileToken?}` -> order view or 404 with one generic message for any mismatch. Nothing is minted or rotated. Limit 10 attempts / 10 min / ipKey; after 3 failed lookups from an ipKey in 10 min, further lookups need a Turnstile token (400 `CAPTCHA_REQUIRED` without one; the form then shows the widget).
- Order view DTO (201 body and lookup response): status + steps, items, subtotal, discountTotal + discountNote, shippingFee (null until confirmed), total, payment method, name + masked phone (`0912 *** 678`), never the address; `amountReissueNote` when present; bank block only for BANK_TRANSFER and status in PENDING/CONFIRMED: bank name, BIN, account no, account name (from settings), content = code; `qrAmount` = total only once CONFIRMED with shipping fee set, else null and the page shows text only, no QR [V2, W1]. Page: `Referrer-Policy: no-referrer`, `noindex`, no caching.
- VietQR (`apps/web/lib/vietqr/emvco.ts`, pure): TLV `id + len(2) + value`; `00=01`, `01=11` (no amount) or `12` (amount), `38{00=A000000727, 01{00=BIN, 01=account}, 02=QRIBFTTA}`, `53=704`, `54=amount?`, `58=VN`, `62{08=content}`, `63=CRC-16/CCITT-FALSE` (poly 0x1021, init 0xFFFF) over the string including `6304`, 4 upper-hex. Tags from FE report s.5 are [U]: verify against a QR generated by the owner's bank app before launch. Content validated `^[A-Z0-9]{1,25}$`. Rendered by `qrcode` (1.5.4) `toString(..., {type:'svg'})` in the browser; account/amount/content always shown as text too. The page renders a QR only with an amount (`01=12` + `54`); the amount-less form (`01=11`) is kept in the encoder only to compare against a bank-app sample fixture. Our own encoder stays the QR source (no third-party QR image host: privacy + availability, report s.3); SePay only notifies.
- Turnstile [RT#5]: widget on the 3 forms (+ lookup after failures); `TurnstileVerifier` calls siteverify with `secret`, `response`, `remoteip`, `idempotency_key`; `dna.turnstile.enabled` defaults **true**; only the test profile sets `false`; dev uses Cloudflare test keys; in the prod profile startup fails if `enabled=false` or the secret is blank.
- Rate limits (per ipKey, 10 min): orders 5 and quotes 5 (successful creates only), contact 3, lookup 10 attempts; cart price 60/min. Client IP from `CF-Connecting-IP` (phase 2).
- State machines (`OrderStatusMachine`, `QuoteStatusMachine`, pure): CONFIRMED requires `shippingFee >= 0`; COD skips PAID; BANK must pass PAID before ENTERED_KIOTVIET; PAID takes an explicit actor: `MANAGER` user with `paid_amount` (note required when `paid_amount != total`), or system actor `BANK_WEBHOOK` only from CONFIRMED with a matched `bank_transaction` whose amount = total; EDITOR rejected [RT#6 amended by W2]; ENTERED_KIOTVIET requires `kiotviet_order_code`; CANCELLED from PAID requires a refund note [RT#6]; COMPLETED/CANCELLED/WON terminal. Line edits (qty, remove) and fee changes: COD in PENDING/CONFIRMED; BANK_TRANSFER only in PENDING, or in CONFIRMED via `POST /api/admin/orders/{id}/reissue-amount {lines?, shippingFee?, reason}` (audit `ORDER_AMOUNT_REISSUE`, sets `amount_reissued_at` + note shown to the customer; rejected after PAID) [RT#6]. Snapshot prices kept, totals recomputed. Every transition -> `audit_log` (`ORDER_STATUS`/`QUOTE_STATUS`, from/to; webhook transitions with `actor_id` null, `actor_name` `BANK_WEBHOOK` and the `bank_transaction` id in `after`); "Lịch sử" tab reads audit rows.
- Admin list: native `UNION ALL` query over quotes and orders with filters + paging (`GET /api/admin/requests`), `GET /api/admin/requests/counters` for the bell (60 s polling).
- Exports via POI (`poi-ooxml` added to `pom.xml` here; phase 4 reuses it): `/api/admin/quotes/{id}/export.xlsx`, `/api/admin/orders/{id}/export.xlsx` (Mã hàng, Tên hàng, ĐVT, SL, Đơn giá, Thành tiền, Giảm (promo per line); footer row "Giảm đã áp" = `discount_total` + note), `GET /api/public/price-list` (JSON for `/bang-gia`) and `/api/public/price-list.xlsx`, both through `PublicPriceRedactor` [RT#4]. Print pages are HTML + print CSS; "In / Lưu PDF" calls `window.print()`; no PDF dependency in `pom.xml` or `package.json` [V6].
- Email [RT#6]: `EmailNotificationAdapter implements NotificationPort` (`spring-boot-starter-mail`, SMTP from env `SPRING_MAIL_*`); plain-text Vietnamese mails with code, customer name, total and an admin link (`dna.site-url`); sent `@Async` after commit, failure logged (data is already in DB; bell still shows it). Phase 7 reuses the port for the bank-settings alert.
- "Nhắn Zalo" = link `https://zalo.me/{phone_norm}` (no Zalo API).

### Bank webhook (SePay) [W1, W2]

Contract per [report](../reports/researcher-261029-bank-webhook-services-report.md) s.2 (SePay webhook page [V]): POST JSON `id, gateway, transactionDate, accountNumber, subAccount, code, content, transferType, description, transferAmount, accumulated, referenceCode`; reply HTTP 200/201 + `{"success": true}` within 30 s.

```
SePay ─POST /api/webhooks/bank/sepay─> Cloudflare ─> Caddy (/api/* -> api) ─> SepayWebhookController
   1 WebhookAuthenticator: header `Authorization: Apikey <key>` vs env keys, constant-time (MessageDigest.isEqual) -> else 401, nothing stored
   2 tx A: insert bank_transaction(status RECEIVED, raw JSON) ; unique (vendor, vendor_tx_id) hit -> 200 {"success":true}, no-op
   3 reply 200 {"success":true}   (matching never changes the reply; failures leave RECEIVED for the reconcile job)
   4 tx B (inline after commit of A): BankTransactionIngestService.process(id)
       PaymentMatcher.match(tx, orderLookup, config) (pure) -> AUTO_PAID(order) | REVIEW(reason) | IGNORED
       AUTO_PAID: lock order FOR UPDATE -> OrderStatusMachine CONFIRMED->PAID (actor BANK_WEBHOOK) + audit + tx MATCHED
                  (order changed meanwhile -> re-match -> REVIEW ALREADY_PAID / NOT_CONFIRMED)
BankReconcileJob (every 30 min) ─SePay transaction API, last 48 h─> same ingest (insert-if-absent + process) ; re-process RECEIVED > 5 min
```

- Endpoint: public, no Turnstile, no session, no CSRF (`/api/webhooks/**` row in the phase-2 URL table); auth only by API key (SePay option "API Key" [V]); HMAC-SHA256 is a documented SePay option [V] whose header/format was not read [U]; can replace the key check behind `WebhookAuthenticator` later. Env `DNA_SEPAY_WEBHOOK_KEYS` holds 1-2 keys (current, next) so the key can be rotated without downtime (runbook, phase 8). Optional IP allowlist from SePay's published list (7 IPv4, 2 IPv6 [V]) is a phase-8 edge option; behind Cloudflare the client IP is `CF-Connecting-IP`, not the TCP peer [U: needs a check of how SePay calls arrive]. In-app limit 120 req/min on the path (`FixedWindowRateLimiter`), body <= 64 KB.
- `PaymentMatcher` (pure, `sales/bank`): content normalisation = NFD strip marks, `đ/Đ`->`D`, uppercase, drop spaces/hyphens/dots/underscores, then the lookup rule from `CodeGenerator.normalize` (`O`->`0`, `I`/`L`->`1`); find all `DNA[0-9A-HJKMNP-TV-Z]{6}`. Exact-match conditions, all required: exactly one distinct code found, order exists, `payment_method = BANK_TRANSFER`, status `CONFIRMED` (amount QR visible, total frozen), `transferAmount == total`, `accountNumber == DNA_SEPAY_ACCOUNT_NO == settings bank.accountNo` (a bank-settings change without updating SePay/env sends everything to REVIEW instead of a wrong PAID), `transferType == "in"`. Review reasons: `NO_CODE`, `MULTIPLE_CODES`, `UNKNOWN_CODE`, `NOT_BANK_TRANSFER`, `NOT_CONFIRMED`, `ALREADY_PAID` (covers duplicate transfers), `AMOUNT_MISMATCH` (under/over), `WRONG_ACCOUNT`, `OUT_WITH_CODE`. Outgoing transfers without any order code -> `IGNORED` (stored, not queued; the company's own payments). SePay's own `code` field (prefix extraction rule [U]) is stored but not trusted; our parser decides. Banks may truncate or alter content (19-char / no-diacritics limits reported [U]): verify with the owner's bank app (step 5) and add the observed content as a matcher fixture.
- Order state: only through `OrderStatusMachine` with an audit row (from/to, actor `BANK_WEBHOOK`); sets `paid_amount` = transfer amount, `paid_via = BANK_WEBHOOK`, `paid_at` = transaction time; `paid_by` null. REVIEW never touches the order. Optimistic `@Version` + row lock make concurrent webhook/reconcile/manual "Đã nhận tiền" safe: the loser sees PAID and goes to REVIEW `ALREADY_PAID`.
- Reconciliation (`BankReconcileJob`, `@Scheduled` every 30 min via phase-2 `AsyncSchedulingConfig`): calls the SePay transaction API (exists per docs index [U]; endpoint, paging and whether calls count against the plan quota [U], confirm in step 10) for the last 48 h and feeds every row through the same ingest (idempotent by vendor id). Webhook loss is assumed possible because SePay's documented retry policy conflicts (7 retries / 5 h vs 8 attempts / ~33 min [U]). Each successful run pings `HC_RECONCILE_PING_URL` (healthchecks.io, phase 8). REVIEW rows older than 24 h without a decision -> one email per row to `notify.ownerEmail` via `NotificationPort.bankReviewPending` (`alerted_at` set, no repeats).
- REVIEW queue (admin, MANAGER only): tab "Giao dịch ngân hàng" on `/admin/requests` with REVIEW / MATCHED / IGNORED filter; row shows time, amount, masked account, content, reason. Actions: **Gắn vào đơn** `POST /api/admin/bank-transactions/{id}/link {orderId, markPaid, note}` -> tx MATCHED + `order_id`; with `markPaid` it runs the normal MANAGER PAID transition (`paid_amount` = Σ linked amounts, note required when != total); **Bỏ qua** `POST /{id}/dismiss {note}` -> IGNORED. Audit `BANK_TX_LINK`, `BANK_TX_DISMISS`. Bell counter includes REVIEW count.
- Config (`SepayProperties`, env only): `DNA_SEPAY_ENABLED` (default false; when false the endpoint returns 404 and the job is off, manual flow only), `DNA_SEPAY_WEBHOOK_KEYS`, `DNA_SEPAY_ACCOUNT_NO`, `DNA_SEPAY_API_TOKEN`; prod startup fails when enabled with a blank key/token/account. Logs mask account numbers (last 4 digits) and never print the `Authorization` header or the raw body.

## Risk Assessment

| Risk | L x I | Mitigation |
|---|---|---|
| VietQR payload rejected by some banks | M x H | Bank-app sample fixture; test 2+ apps; text fallback always visible |
| Customer pays a stale amount after staff edit [RT#6] | M x H | Freeze after amount QR; explicit re-issue with visible note; `paid_amount` mismatch warning |
| Insider redirects payments [RT#6] | L x H | Manual PAID and bank settings MANAGER-only; webhook PAID only on exact match incl. receiving account = env = settings; bank change needs password + email alert (phase 7); audit log |
| Forged webhook marks an unpaid order PAID [W2] | L x H | API key (constant-time, env, rotatable) over HTTPS via Cloudflare; exact match on code + amount + account + direction; audit actor `BANK_WEBHOOK`; optional SePay IP allowlist (phase 8) [U]; HMAC option later |
| Webhook lost or late (SePay retry window 5 h vs ~33 min conflict [U]) | M x M | Persist-first, reconcile job every 30 min over 48 h, healthchecks ping, manual "Đã nhận tiền" fallback |
| Bank alters transfer content so the code is not found | M x M | Normalised matcher, owner-bank fixture (step 5); unmatched -> REVIEW, never wrong PAID; REVIEW > 24 h -> email |
| SePay does not support the owner's bank / TNHH corporate account [U] | M x H | Check before step 10 (plan.md open items); fallback Casso (contract unread [U]) or manual matching only; rest of phase 6 does not depend on it (`DNA_SEPAY_ENABLED=false`) |
| REVIEW noise from non-order incoming credits | M x L | Reason filter in the queue; dismiss with note; volume counted against SePay plan quota (report s.4) |
| Price changed between view and submit | M x M | 409 `PRICE_CHANGED` with new lines before Turnstile is consumed; UI shows diff and asks to confirm |
| Order data seen by someone with the code [RT#5] | L x M | Code + phone required every time; lookup rate limit + Turnstile after failures; page shows masked phone, never the address |
| Spam floods quote/order queues | M x M | Honeypot + Turnstile + per-IP limit; Cloudflare rule in phase 8 |
| Owner misses new orders (email in spam / SMTP down) [RT#6] | M x H | Go-live checklist test mail; admin bell as backup; SPF/DKIM on the sending domain |
| Scope creep (customer accounts, online payment gateway) | M x M | Section D "không làm"; refuse in review; SePay is a notifier, not a gateway (money stays in the company account) [W1] |

Rollback: storefront not public until phase 8; V40-V43 additive; revert commits. Webhook alone: set `DNA_SEPAY_ENABLED=false` (endpoint 404, job off) and switch off the SePay webhook; manual MANAGER "Đã nhận tiền" continues; `bank_transaction` rows stay for audit.
